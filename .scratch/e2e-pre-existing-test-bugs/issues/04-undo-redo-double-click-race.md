## What to build

The scoreboard's UNDO and REDO buttons are not gated by an `isSubmitting` lifecycle, the way the OK button (throw submit) is. `handleUndo` and `handleRedo` in the scoreboard are bare `await undoThrow(...)` / `await redoThrow(...)` calls with no state to disable the button or show a spinner while the server action runs. A user (or a test) that taps UNDO twice in quick succession fires two concurrent `undoThrow` server actions, each opening a Prisma transaction and calling `revalidatePath`. The result is non-deterministic — depending on which transaction commits first, the leg may end up unwound by one or two steps.

The current E2E test for UNDO/REDO (in `match-flow.spec.ts`) works around this by *not* clicking UNDO or REDO twice in a row without first awaiting a server-rendered post-action signal. That workaround was added in the fix for `02-match-flow-spec-undo-wait-race.md`. The production-side gap remains: the scoreboard's UNDO and REDO buttons should mirror the OK button's `isSubmitting` pattern (a single `useState` boolean, set true before the server action and false in `finally`, gating the button's `disabled` prop and driving the existing `GamepadButton`'s `isLoading` spinner prop). With this in place, a double-click during the in-flight server action is a no-op because the second click is dispatched on a disabled button.

## Acceptance criteria

- [ ] The scoreboard's UNDO button is disabled and shows the existing `GamepadButton` spinner (`isLoading={isSubmitting}`) for the full duration of an in-flight `undoThrow` server action, mirroring the OK button's existing behaviour.
- [ ] The scoreboard's REDO button is disabled and shows the existing `GamepadButton` spinner for the full duration of an in-flight `redoThrow` server action.
- [ ] A second click on UNDO or REDO dispatched while the first server action is in flight has no effect (the button is disabled; the second click does not enqueue a second server action).
- [ ] After the server action resolves (success or throw), the button re-enables and the spinner disappears, even if the action threw — i.e. the disable/spinner cleanup happens in a `finally` block, matching the OK button's pattern.
- [ ] A unit or integration test covers the double-click case for UNDO: dispatch two `undoThrow` actions back-to-back without awaiting the first, and assert that the second is a no-op at the UI level (e.g. via the existing scoreboard unit tests or a new test under `app/tournaments/[id]/tables/[table]/__tests__/`).
- [ ] The "opens a tournament, plays a match" E2E test continues to pass deterministically after the change.
- [ ] `npm test` and `npm run lint` are clean.

## Why

The narrow fix in `02-match-flow-spec-undo-wait-race.md` anchors the test waits to server-rendered post-action signals, which makes the *test* deterministic. It does not address the underlying production gap: UNDO and REDO are the only mutating actions on the scoreboard that are not gated by an in-flight state. For a real scorekeeper tapping fast on a tablet (the scoreboard is tablet-optimised per `DARTS.md`), a double-click is a realistic user input and the current behaviour is silent data corruption.
