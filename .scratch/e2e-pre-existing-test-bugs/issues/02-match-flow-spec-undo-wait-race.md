## Agent Brief

**Category:** bug
**Summary:** The "opens a tournament, plays a match, and closes it" E2E test races on `waitForActivePlayer` immediately after UNDO/REDO clicks, because no server-rendered post-action signal is awaited between the click and the active-player assertion.

**Current behavior:**
After `await page.getByRole('button', { name: 'UNDO' }).click()` the test calls `await waitForActivePlayer(page, playerAId)`, which polls `getByTestId('player-card-${playerAId}').toHaveAttribute('data-active', 'true')`. The UNDO server action returns, `revalidatePath` invalidates the route, and the new server-rendered HTML eventually swaps the `data-active` attribute. The test was passing in dev mode because the slow dev HMR / compile time gave the page enough wall-clock to settle before the assertion fired. After the containerised test runner switched to a production `next start` build, the test fails deterministically (sometimes after Playwright retries) at the same `waitForActivePlayer` call — the assertion catches a window where the new HTML has not yet been swapped in, or where the swap has happened but the React reconciliation has not yet committed the new `data-active` to the DOM.

The root cause is that the test relies on `data-active` (an attribute on a server-rendered element) to detect that the UNDO has been applied, but does not await any *other* post-undo signal first. The throw-history UI, by contrast, contains a server-rendered "undone" chip with a `data-testid` prefix `scoreboard-history-undone-` that appears the moment the new server HTML lands. The test already asserts on this chip — but on the line *after* the `waitForActivePlayer` call, which is too late.

**Desired behavior:**
After each UNDO/REDO click in the "opens a tournament" test, the test first awaits a server-rendered post-action signal (the undone chip after UNDO, the absence of an undone chip after REDO), then asserts on `data-active`. Both signals are server-rendered and can only be present after `revalidatePath` has produced a new render. No hardcoded sleeps, no `page.waitForTimeout`, no changes to production code.

The three racy `waitForActivePlayer` calls in the test are at:
- after the first UNDO click (expects player A active)
- after the REDO click (expects player B active)
- after the second UNDO click (expects player A active)

All three should be preceded by an appropriate post-action signal wait. Other `waitForActivePlayer` calls in the file (after `playTurn` and after start-player selection) are not racy because they are preceded by `enterScore`'s own server-rendered post-throw signal (`scoreboard-input` reset to `0`, or `'Darts used:'` visible for checkouts) — leave them alone.

**Key interfaces:**
- The test helper `waitForActivePlayer` in `tests/e2e/match-flow.spec.ts` is an `expect.toHaveAttribute` poll on `getByTestId('player-card-${playerId}')`. No change to this helper; the fix is at the call sites, not in the helper.
- The server-rendered undone chip selector `[data-testid^="scoreboard-history-undone-"]` in the scoreboard's `ThrowHistory` component (rendered when `playerThrow.status === 'undone'`). The throw history is re-rendered by `revalidatePath('/tables/[table]', 'page')` after each UNDO/REDO server action. The selector is the natural post-undo signal.
- The server-rendered active chip selector `[data-testid^="scoreboard-history-active-"]` (or equivalently the absence of any `scoreboard-history-undone-` chip) is the natural post-REDO signal.
- The scoreboard's UNDO and REDO server actions (`undoThrow` and `redoThrow` in `app/lib/playerThrow.ts`) and the scoreboard's `handleUndo` / `handleRedo` wrappers in `app/tournaments/[id]/tables/[table]/scoreboard.tsx`. **No production-code changes are required for this fix.** The `isSubmitting` gap on UNDO/REDO is a separate follow-up issue and is explicitly out of scope (see "Out of scope" below).
