## Agent Brief

**Category:** bug
**Summary:** The "loading spinner when CueScore calls are slow" E2E test races because it asserts against a spinner window that is only as long as the Prisma transaction. Coverage of the spinner UX is incomplete: the *non-checkout* submit path (Prisma only) and the *checkout* submit path (Prisma + CueScore roundtrip) must both be covered with deterministic, asserted-against durations.

**Current behavior:**
A single E2E test in `match-flow.spec.ts` is named "shows loading spinner when CueScore calls are slow". It sets a 2-second delay on the fake `updateMatchScore` method, then has the player enter a 100-point throw on a fresh 501 leg. Because the throw does not close the leg, `addThrowAction` never reaches the CueScore `setScore` call, so the 2-second delay is never observed. The spinner is visible only for the (fast) Prisma transaction, and the `toBeDisabled` / `toBeVisible` assertions race against the buttons re-enabling. The test passed in dev mode only because dev HMR happened to make the page slow enough to satisfy the timing.

**Desired behavior:**
Two E2E tests replace the current one, both deterministic across at least 3 consecutive containerised E2E runs with no retries, and both using real page-state signals (no `page.waitForTimeout`):

1. **"shows loading spinner during a non-checkout throw submission"** — a non-checkout throw (e.g. 100 on a 501 leg), with the Prisma transaction artificially delayed to make the spinner window observable. Asserts the spinner appears immediately after OK, all action buttons (UNDO, REDO, OK) are disabled, and the buttons re-enable after the delay completes. The Prisma delay is the only way to make this window observable — CueScore delays do not apply because non-checkout throws do not call CueScore.
2. **"shows loading spinner when a CueScore call is slow (checkout throw)"** — a checkout throw (3-dart checkout of 141, reached after one prior non-checkout 360 throw that leaves the player at remaining 141), with `updateMatchScore` delayed by ≥ 2 seconds. Asserts the spinner stays visible and all action buttons stay disabled for the full duration of the CueScore delay, then re-enable. Uses the existing `playTurn(360, …)` + `playTurn(141, …, true)` pattern from the rest of the file.

**Key interfaces:**
- `addThrowAction` in `app/lib/playerThrow.ts` — a server action that runs `prisma.$transaction(...)` and (only on checkout) `setScore(...)`. The test-only delay hook lives at the top of this function, before the transaction, gated by the same three-env-var rule as the existing `/api/test/cuescore` route.
- A new in-app test API surface for delaying the Prisma transaction, parallel to `app/api/test/cuescore/route.ts`. The gating function `isTestCueScoreApiEnabled()` should be extracted to a shared module (e.g. `app/lib/integrations/cuescore/test-mode.ts`) and reused by both routes and the new test-only branch in `addThrowAction`. Per-test isolation is required: state is keyed by `tournamentId` (matching the existing `FakeCueScoreGateway` pattern) so parallel Playwright workers do not collide.
- `FakeCueScoreGateway.setDelayMs(method, ms)` in `app/lib/integrations/cuescore/fake.ts` — already exposed via the `/api/test/cuescore` POST route. No changes needed for the checkout case; the existing `resetFakeCueScore(request, tournamentId, { updateMatchScore: 2000 })` helper signature is reused.
- `playTurn` / `enterScore` / `waitForActivePlayer` helpers in `tests/e2e/match-flow.spec.ts` — reuse for the checkout setup. No new helpers needed for the throw sequence; both tests use the established pattern.
- The scoreboard's `isSubmitting` state in `app/tournaments/[id]/tables/[table]/scoreboard.tsx` — covers the full `addThrowAction` call (Prisma + CueScore + revalidate). Both tests assert against `svg.animate-spin`, `getByRole('button', { name: 'UNDO', exact: true })`, `getByRole('button', { name: 'REDO', exact: true })`, and the OK button, matching the existing assertion style.

**Acceptance criteria:**
