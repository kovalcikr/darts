## What to build

The "loading spinner when CueScore calls are slow" E2E test sets a delay on the wrong CueScore method. It delays `updateMatchScore` by 2 seconds, then throws a non-checkout 100-point score, but `addThrowAction` only calls `setScore` (which dispatches to `updateMatchScore`) when the throw closes the leg. So the 2-second delay never fires, the spinner only stays visible for the (fast) Prisma transaction, and the test's `toBeDisabled` assertions race against the button re-enabling.

The test was passing in dev mode because the dev server's slow HMR happened to keep the spinner visible long enough to satisfy the assertions. After the containerised test runner was switched to a production build, the test fails deterministically.

The right fix is to make the test exercise a path that actually calls the delayed CueScore method. Throw a checkout score so `setScore` → `updateMatchScore` fires, OR delay a method that is actually called for non-checkout throws (currently none in `addThrowAction` for non-checkout throws — it only touches Prisma and `revalidatePath`).
