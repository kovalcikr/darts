## Agent Brief

**Category:** bug
**Summary:** Three E2E tests in `dashboard-cache-revalidate.spec.ts` race between `page.goto('/tables/N')` and the subsequent `start-player-${...}.click()`: the scoreboard's `ChoosePlayer` UI has not mounted when the click fires, and the click is a no-op (the page snapshot at failure shows the table listing, not the scoreboard).

**Current behavior:**
The E2E tests "dashboard cache revalidation shows updated throw after addThrowAction", "dashboard cache revalidation shows restored state after undo", and "dashboard cache invalidation is isolated between tables" all open a table page (`/tables/1` or `/tables/2`) and immediately call `await tablePage.getByTestId(\`start-player-${playerAId}\`).click()`. In production, the Next.js client has not yet mounted the scoreboard's `ChoosePlayer` component by the time the click fires — the page snapshot at failure shows the `Tables` listing (with `Scoreboard Table N` links), not the scoreboard. The click finds no `start-player-` testid and the test's subsequent `expect(getByRole('button', { name: 'UNDO' })).toBeVisible()` fails.

The tests were passing in dev mode because the dev server's slow HMR / compile time gave the scoreboard enough wall-clock to mount before the click. After the containerised test runner switched to a `next start` production build, the scoreboard mounts faster than the test's click resolves. The "dashboard cache revalidation shows new match after startMatch" test (line 36) is the exception — it passes by accident of doing several dashboard polls (`expect(table1).toContainText(...)` and `toHaveCount(0)`) between the `goto` and the `start-player-` click, which gives the table page time to mount.

**Desired behavior:**
Every `page.goto('/tables/N')` followed by a `getByTestId(\`start-player-${...}\`).click()` in this file is preceded by an explicit await on a server-rendered post-mount signal — the text `'First to play:'` rendered by the `ChoosePlayer` component. The wait is the same anchor the UI test suite already uses (`tests/ui/scoreboard.spec.ts:13`, in `openStartedTableOne`): it can only appear once the scoreboard's pre-start UI has fully mounted, and it disappears the moment a `start-player-` button is clicked, so it is a one-shot, server-rendered signal.

The first test in the file (the "shows new match after startMatch" test) does not need a new wait — its existing dashboard polls between the goto and the click already provide the necessary mount time. Leave it alone.
